# The review cycle

When you delegate an issue to an agent in the hosted sandbox, the work does not
go directly to a pull request. It goes through a loop first:

1. **Implement.** An agent gets the issue, its Definition of Done, and the
   commands of the repository. It writes the change.
2. **Verify.** Vantik runs the checks of the module against the tree that the
   agent left. The checks are the test, typecheck, lint and build commands that
   the module declares. Vantik runs them, not the agent. An agent can think that
   it ran the tests when it did not.
3. **Review.** A *second* agent, in the same sandbox, reads the diff and
   compares it with the issue. This agent did not write the code, and it must
   not change it. It gets the result of the checks as fact.
4. **Revise.** An implementer gets the findings of the reviewer, and fixes
   them. Then the loop goes back to step 2.

The loop stops when the reviewer accepts the work, or when one of the
conditions in [When the loop stops](#when-the-loop-stops) occurs.

To start a run, read [Delegate an issue to an agent](/agents/delegating-an-issue).

## Why a second agent

An agent that examines its own answer again is not a check. Without a signal
from a real execution, self-correction does not make code better, and it can
make it worse. If you challenge a model about a correct answer, the model can
abandon the correct answer. The review pass has value because a different agent
does it. That agent never saw the reasoning. It gets the issue and the tree, as
a human reviewer does.

The two agents get different instructions and different skills. Vantik never
tells the implementer how to review. An implementer that grades its own diff
removes the only independent read. Vantik never gives the reviewer the skill
to write changes, because the reviewer must not make a change.

## What a finding must have

Vantik discards a review finding unless it cites a location, for example
`file.ts:123`, or a command in backticks. Vantik keeps a maximum of 12 findings,
the most severe first.

This rule is not about format. A reviewer that opened the file writes a
different finding from a reviewer that only read the diff. The citation makes
the reviewer do the first. It also protects the next pass. If an implementer
gets "consider whether this is idiomatic", it can spend a pass, and your money,
on a change that nobody needed.

## When the loop stops

**It accepts the work** when the reviewer accepts it *and* the checks did not
fail. If the module declares no checks, the decision of the reviewer is
sufficient. A finding of high severity stops the acceptance, also when the
reviewer accepted the work. A reviewer that accepts a tree with failed tests
contradicts a real execution, and the execution wins.

**It stops and asks for a person** in these cases. The run then ends with the
status **Needs a human**:

- The reviewer gave no verdict that Vantik can read. "The reviewer did not
  answer" and "the reviewer said yes" never become the same outcome.
- The reviewer rejected the work but cited nothing, and the checks did not
  fail. Then nothing specific can go back to the implementer.
- The run reached its spend ceiling, its wall clock, or its number of passes.
- Two passes in a row changed neither the tree nor the result of the checks.
  Then another pass cannot change more.
- Less than 90 seconds remained before a pass or a review.
- The model provider refused the reviewer.
- A pass after the first one crashed, or the provider refused it.

If the reviewer rejected the work and cited nothing, but the checks failed,
the loop does not stop. Another revise pass runs, and it gets the failed checks.
The ceilings still apply.

In each of these cases, Vantik still delivers the work. Vantik pushes the
branch, and opens the pull request if the host supports pull requests. The work
is real, but nothing accepted it. The pull request and the comment on the issue
say so. They also list the findings that the last review still had. The person
who takes the work then starts from what is wrong, not from the diff.

If you do not want the work, click **Reject** on the page of the run. Vantik
closes the pull request with a comment that tells why, and deletes the branch.
**Reject and retry** then starts a new attempt. If a person added commits to
the branch after the run, Vantik keeps the branch. Vantik keeps the run and its
record.

![The Reject this work dialog, with the Cancel, Reject, and Reject and retry
buttons.](/img/docs/agents/clean-up.png)

After you reject the work, the run shows the status **Rejected**. The outcome
card shows "Rejected: the work was not kept", and tells who rejected it and
when. On the server, the run keeps the status **Needs a human**.

![A rejected run. The reviewer cited nothing, so the run went to a person, who
rejected it. The outcome card tells that Vantik closed the pull request and
deleted the branch.](/img/docs/agents/run-rejected.png)

The same dialog shows as **Clean up** on a run that failed, stopped or went
away, if the run recorded a branch. The hosted sandbox records no branch on
such a run. You do not need to clean up before a retry, because each attempt
pushes to its own branch. Read
[After a run](/agents/delegating-an-issue#after-a-run).

**It fails** in these cases:

- The first pass crashes, or the model provider refuses it.
- The agent changed nothing.
- The environment does not build.
- The host rejects the push.
- The tree is too large to push.

A crash on a *later* pass does not fail the run. It stops the loop, and Vantik
delivers the work of the earlier passes.

## The budget

| Ceiling | Default | What it limits | Where you set it |
| --- | --- | --- | --- |
| Review passes | 3 | The number of times through the loop before a person must look. | **Settings → Agents**, in **Review passes**. |
| Spend per issue | $5 | All the cost of one attempt, in all passes. | **Settings → Agents**, in **Spend per issue (USD)**. |
| Wall clock | 30 minutes | The full run, with the fetch of the repository. | No field in **Settings → Agents** changes it. |

These fields are in the section **How the work is checked**. Only a workspace
admin can change them.

The ceilings apply to the *full cycle*, not to one call to the agent. Each
review adds the cost of a second agent to the cost of the issue. Each revise
pass adds more cost. To stop this cost, turn off the review. Read
[How to turn it off](#how-to-turn-it-off).

A run that reaches a ceiling does not lose its work. It hands the work over.

### How Vantik measures the spend

Vantik adds the cost of each call to the model:

- If the provider reports the cost that it bills, Vantik uses that cost. A
  gateway, for example OpenRouter, reports it.
- If the provider does not report it, Vantik uses the price of the model from
  the catalog of the agent harness, and the token counts.

Vantik checks the spend between passes. So a pass can end a little over the
ceiling.

## How to turn it off

In **Settings → Agents**, under **How the work is checked**, turn off **Review
every change before handing it back**. Then the cycle stops for the workspace.
Vantik delivers the first attempt as it is. When the switch is off, the fields
for the passes and the spend do not show.

The switch is on by default. A pull request that nothing read is the failure
that hosted runs must prevent. But a workspace that wants the less expensive
method can turn it off.

## What you can see afterwards

The page of the run shows the cycle in two places:

- **The stepper** shows the stages **Set up**, **Work**, **Check**, **Review**
  and **Hand back**. The time of each stage adds all the passes. A revise pass
  counts as **Work**. A stage that the run did not need shows **skipped**.
- **Activity** shows each event in order, with the steps of the cycle. For
  example: "Running the repository’s own checks", "Reviewing the work against
  the issue", and "The reviewer found 2 thing(s) to fix".

![The page of a run while it works. The stepper shows the Check stage, and
Activity shows the steps of the run.](/img/docs/agents/run-running.png)
