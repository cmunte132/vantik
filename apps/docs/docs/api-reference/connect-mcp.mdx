Vantik speaks the [Model Context Protocol](https://modelcontextprotocol.io) so
an LLM agent — Claude Code, Cursor, or anything that speaks MCP — can create,
pick up, note and close issues, and search past work, without you wiring up the
REST API by hand. The server exposes a task-shaped set of tools; the messy
parts (resolving `ENG-42` to an id, markdown conversion, posting a resolution
before closing) happen on the server side.

The endpoint is:

```
POST /v1/mcp
```

It is a stateless [Streamable HTTP](https://modelcontextprotocol.io/docs/concepts/transports)
MCP server and uses the same [personal access token
authentication](./overview.mdx) as the rest of the API — the token travels in
the `Authorization` header.

## Get a token

Provision one in **Vantik → Settings → Agents**. An agent account is a distinct
identity in the workspace, so the issues it creates and the notes it writes are
attributed to the agent rather than to you. Creating one shows the token once,
along with a ready-to-paste `.mcp.json` and `claude mcp add` command — copy
them then, as the token is not retrievable afterwards.

:::note
Provisioning an agent is admin-only. If you don't see **Settings → Agents**,
ask a workspace admin to create the agent and hand you its config.
:::

## Connect Claude Code

Add the server to a project's `.mcp.json` (replace the host and token):

```json
{
  "mcpServers": {
    "vantik": {
      "type": "http",
      "url": "https://your-vantik-host/api/v1/mcp",
      "headers": { "Authorization": "Bearer tg_pat_…" }
    }
  }
}
```

Or register it from the command line:

```bash
claude mcp add --transport http vantik https://your-vantik-host/api/v1/mcp \
  --header "Authorization: Bearer tg_pat_…"
```

:::warning
A project's `.mcp.json` is usually committed, and this one holds a live token
that can read and write the workspace. Either keep it out of version control or
register the server per-user instead — `claude mcp add` writes to `~/.claude.json`,
which is not in the repo. If a token does get committed, revoke that agent in
**Settings → Agents** and generate a new one.
:::

## Connect another client

Any MCP client that supports the Streamable HTTP transport works the same way:
point it at `https://your-vantik-host/api/v1/mcp` and send the token as an
`Authorization: Bearer` header. The `/api` prefix is the webapp proxy in front
of the server; if you call the server directly, drop it and use `/v1/mcp`.

## The tools

| Tool | What it does |
| --- | --- |
| `list_tasks` | List tasks (lean rows), filterable by team, assignee, state, labels, priority, project. |
| `get_task` | Everything about one task in a single call: description, notes, history, sub-tasks, relations. |
| `search_tasks` | Search titles, descriptions **and notes**; set `stateCategory: ["COMPLETED"]` to find prior fixes with their resolution. |
| `find_similar_tasks` | Prior tasks resembling one, with how each was resolved. |
| `create_task` | File an issue. Holds the issue to a floor — a real description, and acceptance criteria for a top-level issue. |
| `update_task` | Change a task's title, description, state, labels, priority, assignee or project. |
| `list_projects` | The workspace's projects — the objectives issues are grouped under. |
| `create_project` | Open a project for an objective that genuinely needs several issues. |
| `pick_up_task` | Take ownership: assign it and move it to the in-progress state. |
| `add_note` | Post a searchable markdown note on a task. |
| `close_task` | Close a task, recording the resolution as a note first so the fix stays findable. |

Everything a tool does maps onto the REST API documented in [Working with
agents](./agents.mdx) — reach for that page when you want the endpoints
underneath, or are building against the API directly instead of over MCP.

## Rate limits

The endpoint is rate limited per token, so an agent stuck in a loop throttles
only itself. Over the limit you get HTTP `429` with a `Retry-After` header and a
JSON-RPC error body carrying the same wait in `data.retryAfter`.

| Variable | Default | What it sets |
| --- | --- | --- |
| `MCP_RATE_LIMIT` | `120` | Requests one token may make per window. `0` turns the limit off. |
| `MCP_RATE_LIMIT_WINDOW_MS` | `60000` | Length of the window, in milliseconds. |

Counters live in the server process, so across several replicas the effective
ceiling is the limit times the replica count. That is enough to stop a runaway
loop; if you need a real quota, put your own limiter in front and set
`MCP_RATE_LIMIT=0`.

## Optional: house style for filing issues

The config above is all an agent needs to read and file issues. Left to itself,
though, an agent tends to file a long tail of one-line tickets — a note it could
have added to an existing issue becomes a new issue, and a single piece of work
arrives as six.

**working-vantik-issues** is a short written guide that pushes the other way: file
fewer, larger issues; group the ones that serve a single objective under a
project; add a note to an existing issue rather than open a near-duplicate; and
say what "done" looks like before filing at all.

**Settings → Agents** hands it to you in whatever form your tool reads — pick the
harness tab and take the download and the one-line install next to it. The server
serves the files at `/v1/agent-skill/:file`:

| Tool | File | Where it goes |
| --- | --- | --- |
| Claude Code | `SKILL.md` | `.claude/skills/working-vantik-issues/SKILL.md` |
| Claude Code | `CLAUDE.md` | `CLAUDE.md`, to keep it always in context instead |
| Cursor | `working-vantik-issues.mdc` | `.cursor/rules/` |
| Codex, and anything else | `AGENTS.md` | your project root |

Two of those are derived on the way out from the same authored snippet, so there
is one source of truth rather than four copies drifting apart. The originals live
in `apps/docs/skills/working-vantik-issues/`.

This sits above the `create_task` tool, which already refuses an issue with no
description or no acceptance criteria. The tool sets a floor; the guide is the
judgment about what to file in the first place.
