An **integration** connects Vantik to a different tool. It does two jobs:

- It **connects**. It holds the account, and the OAuth flow or the form that
  makes the account.
- It **reacts**. When an issue changes, it sends the change out. When a
  webhook comes in, it brings the data in.

The code of the two jobs is in one directory,
`apps/server/src/integrations/<slug>`, and it ships with the server. The
server loads an integration by the `slug` of its row, and calls it.

## What ships

| Integration | What it does | Read |
| --- | --- | --- |
| GitHub | Links pull requests to issues, opens issues in a paired repository, and is a source of repositories | [GitHub](/integrations/github) |
| Git remote | Repositories on Forgejo, Gitea, GitLab or a different git host over HTTP or HTTPS | [Git hosts](/integrations/git-hosts) |
| Local repository | A git repository on the disk of the machine that runs the server | [Local repositories](/integrations/local-repositories) |
| Email | Makes a triage issue from an email in a Gmail mailbox | [Email](/integrations/email) |
| Discord | Adds the messages of a linked channel as comments | [Discord](/integrations/discord) |
| Bug Enricher | Writes a possible resolution on a new issue with the `bug` label. No third party | [Bug Enricher](/integrations/bug-enricher) |

## How to turn one on

Open **Settings → Integrations**. Each integration shows as a card. Click
**View** on a card to open the page of the integration.

![The Integrations settings, with a card for each
integration](/img/docs/settings/integrations.png)

The page of an integration shows one of these controls:

- **Connect.** GitHub, Email and Discord start an OAuth flow.
- **A form.** **Local repository** takes a path. **Git remote** takes the
  address of a host and a token. These two have no **Connect** button.
- **Turn on.** The Bug Enricher has no third party, so it needs no account.

An integration that needs credentials from the operator of the server shows
**Needs credentials** on its card. Its page shows **Not available on this
deployment**, with the names of the two environment variables to set.

The connection applies to this workspace only. After that, the integration
reacts to the changes that its code declares:

- `onRecord` names the changes that it wants, for example a new issue or a
  new comment. Each connected account of the integration gets them.
- `webhooks` says that it takes the deliveries of its vendor. A delivery goes
  to the one workspace whose account it names.

An integration writes as a bot member with the name of the integration. So
its issues and comments show where they came from.

### Team mappings

GitHub and Email send work to teams. After you connect the workspace account,
the page of the integration shows **Team mappings**. Pair a GitHub repository
or an email address tag with a team. You can pair or unpair only a team that
you are a member of, because a pair decides where the issues of that team go.
When you connect an account again, Vantik keeps its pairs.

## What an integration can do

An integration gets a context, and asks the server to act for it. It holds no
database connection and no credential.

| Capability | What it is for |
| --- | --- |
| `issues`, `comments` | Make and change the work |
| `links` | The link between an issue and the thing that it mirrors |
| `workspace` | Teams, users, labels and workflows |
| `account` | The connected account |
| `vendor` | Calls to the third party |
| `attachments`, `ai`, `log` | Files, the model and the log |

`vendor.fetch` is the most important capability. The integration says which
address to call. The server adds the credential, and it refuses each host that
the integration did not declare. So an integration never holds a token.

## How to write an integration

An integration ships with the server. To write one, add a directory and open a
pull request. You do not deploy it separately.

Each directory exports a default handler. An integration that reacts to
changes or to webhooks also exports a `pluginSpec`:

- The `pluginSpec` gives the slug, the hosts that the integration can call,
  how the server makes its credential, and its `onRecord` and `webhooks`.
- The handler takes an event and the context.

To suggest an integration, open an issue on GitHub.
