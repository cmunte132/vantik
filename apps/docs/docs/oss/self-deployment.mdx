## Overview

Vantik ships as a single Docker Compose stack in the main repository. It runs
the webapp, the API server, and all backing services (PostgreSQL, Redis,
SuperTokens, Typesense), and the server applies database migrations on
startup — no separate deployment repo or setup script is needed.

This guide gets you a working deployment quickly. Scaling, backups, and
hardening beyond the basics are up to you.

## Requirements

- Docker, or Podman with the compose provider (a Podman VM needs at least
  8 GB of memory to build the images)
- 4 CPU / 8 GB RAM is a comfortable baseline

## Instructions

1. Clone the repository and create your `.env`:

```bash
git clone https://github.com/cmunte132/vantik.git
cd vantik
cp .env.example .env
```

2. For anything beyond a localhost test, edit `.env`:

   - Set `FRONTEND_HOST` and `BACKEND_HOST` to your domain
   - Change `POSTGRES_PASSWORD`, `TYPESENSE_API_KEY`, and `TRIGGER_TOKEN`

3. Start the stack:

```bash
docker compose up -d
```

4. Open the webapp (http://localhost:3000 by default, or your
   `FRONTEND_HOST`) and sign in with your email address. Without SMTP
   configured, the magic login link is printed to the server log:

```bash
docker compose logs server | grep -A5 "magic link"
```

## Signing in

There are two ways in, and both are available on a fresh install.

**Email code or magic link.** Enter an address and Vantik emails a six-digit
code and a link. This needs [SMTP](#email-smtp) to be configured, or the code
lands in the server log instead.

**Passkey.** Authenticate with Touch ID, Windows Hello, or a security key. No
mail server is involved, which makes it the practical choice for a single-user
or local install where SMTP is never set up. Sign in with a passkey from the
login screen, or add one to an existing account under **Settings → Security**.

A passkey is bound to the hostname the browser sees, taken from
`FRONTEND_HOST`. Reaching the same instance on a different domain means the
browser will not offer the passkeys registered on the old one, so set
`FRONTEND_HOST` before people enrol. WebAuthn also requires a secure context:
HTTPS in production, though `localhost` is exempt.

Each account holds one passkey, alongside the email code that always keeps
working — so losing a device is not a lockout. To move a passkey to a new
device, remove it under **Settings → Security** and enrol the new one.

By default anyone can create an account by registering a passkey. To run an
invite-only instance, turn that off:

```bash
PASSKEY_SIGNUP_ENABLED=false
```

People then arrive through an invite or a login code, and add a passkey
afterwards from Settings.

## Optional services

Everything below is optional. The server logs an error and continues if a
service is not configured.

### Email (SMTP)

Magic-link logins and notification emails are sent via SMTP when configured;
otherwise login links land in the server log. A [passkey](#signing-in) skips
email altogether, so a single-user install can leave this unset. Any provider
that supports SMTP authentication works (Gmail, Amazon SES, SendGrid, ...):

```bash
SMTP_HOST=your-smtp-host
SMTP_PORT=587
SMTP_USER=your-smtp-username
SMTP_PASSWORD=your-smtp-password
SMTP_DEFAULT_FROM=noreply@yourdomain.com
```

### AI features

AI features (title generation, description elaboration, breaking issues into
sub-issues, filter suggestions) talk to one OpenAI-compatible endpoint. Which
one is yours to choose — hosted or on your own hardware, one place to set it:

```bash
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=your-key

# Vantik asks for a role, never a model name. Point each role wherever you
# like; the ids are whatever your endpoint serves.
LLM_MODEL_FAST=openai/gpt-4o-mini
LLM_MODEL_SMART=openai/gpt-4o
```

`fast` handles the short, frequent calls — titles, labels, filters. `smart`
handles the ones worth paying for — descriptions, sub-issues. Pointing both at
the same model is perfectly reasonable.

The four setups people run:

| Setup | `LLM_BASE_URL` | `LLM_API_KEY` | Notes |
| --- | --- | --- | --- |
| OpenRouter | `https://openrouter.ai/api/v1` | your OpenRouter key | One key, most models. Ids are namespaced, e.g. `anthropic/claude-sonnet-4.5`. |
| OpenAI | `https://api.openai.com/v1` | your OpenAI key | Ids are bare, e.g. `gpt-4o-mini`. |
| LM Studio | `http://localhost:1234/v1` | any placeholder | Nothing leaves the machine. Use the id shown in LM Studio's server tab. |
| Ollama | `http://localhost:11434/v1` | any placeholder | Same, e.g. `gemma2:2b`. Pull the model before pointing a role at it. |

Anything else speaking the same API — vLLM, LiteLLM, a corporate gateway —
works on the same four variables.

Local servers ignore the key but still expect the header, so set
`LLM_API_KEY` to any non-empty string for those.

:::note
Leave these unset and the interface simply has no AI in it — no generate-title
button, no AI filter, no AI entries in the editor's slash menu. Nothing is
shown that cannot work. Set them later and the features appear on the next page
load, with no rebuild: the browser reads this at runtime from
`/api/v1/config`.

Everything else is unaffected. Creating an issue without a title still works,
it just does not get one written for you, and issue suggestions still return
assignees from search, only without label suggestions.

A request that reaches an AI endpoint anyway — a direct API call, or an action
deployed against an older server — fails with an error naming the missing
variable rather than answering with a model nobody chose.
:::

Two optional settings, read only by OpenRouter, attribute usage to your install
on its dashboard and public leaderboards:

```bash
LLM_APP_URL=https://vantik.example.com
LLM_APP_NAME=Vantik
```

Search needs no API key and no external service. Typesense generates the
embeddings in-process with its built-in `ts/all-MiniLM-L12-v2` model, so issue
titles, descriptions and comments never leave your deployment.

To rebuild the search index, delete the Typesense `issues` collection and
restart the server — on boot the server recreates the collection and re-indexes
every workspace from Postgres:

```bash
curl -X DELETE \
  -H "X-TYPESENSE-API-KEY: $TYPESENSE_API_KEY" \
  http://localhost:8108/collections/issues
```

The same rebuild happens automatically when a server upgrade adds fields to the
search schema — the collection is detected as stale, dropped and refilled.

### File attachments

Issue attachments are stored in Google Cloud Storage or Amazon S3. Without a
configured provider, attachment uploads are unavailable — everything else
works.

```bash
# Google Cloud Storage
STORAGE_PROVIDER=GCP
BUCKET_NAME=your-bucket-name
GCP_SERVICE_ACCOUNT_FILE=/path/to/service-account.json  # Storage Object Admin role
PUBLIC_ATTACHMENT_URL=https://your-domain.com/api

# Amazon S3
STORAGE_PROVIDER=AWS
BUCKET_NAME=your-bucket-name
AWS_REGION=your-region
AWS_ACCESS_KEY_ID=your-access-key
AWS_SECRET_ACCESS_KEY=your-secret-key
PUBLIC_ATTACHMENT_URL=https://your-domain.com/api
```

Your bucket needs a CORS configuration allowing your frontend origin:

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "POST", "DELETE", "HEAD"],
    "AllowedOrigins": ["https://your-domain.com"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

### Background jobs (trigger.dev)

[Actions](/docs/actions/overview) — the automation framework — and some
background jobs (user notifications, automated cycle transitions, scheduled
tasks) run on [trigger.dev](https://trigger.dev). Core issue tracking works
without it.

To enable, deploy trigger.dev yourself
([self-hosting guide](https://trigger.dev/docs/self-hosting)) and point
Vantik at it in `.env`:

```bash
TRIGGER_API_URL=https://your-trigger-instance
TRIGGER_DATABASE_URL=postgresql://user:pass@host/trigger
```

:::note
The automation subsystem is being reworked in this fork (see the
[roadmap](https://github.com/cmunte132/vantik#roadmap-planned-direction-not-yet-built)),
so treat trigger.dev integration as legacy-supported rather than the
long-term direction.
:::

## Observability

### Logs

The server writes JSON to stdout, one object per line, at the level set by
`LOG_LEVEL`. Collect it however your platform collects container logs — no
configuration is needed.

Each line carries the correlation fields the request arrived with: `reqId`
(mirrored from `x-request-id`, generated if the caller did not send one and
echoed back on the response), `wId` for the workspace, `aId` for the acting
user, and `opName` for the endpoint. When tracing is on, `traceId` and `spanId`
are included too, so any log line can be pivoted to the trace it belongs to.

Setting `OTEL_EXPORTER_OTLP_ENDPOINT` additionally exports every line over OTLP,
carrying the same correlation fields as record attributes. This **adds** a sink
rather than replacing one — stdout is written either way, so collecting container
logs the usual way keeps working and needs no configuration. There is no log
shipper to run and no container socket to mount.

:::caution Upgrading
Logs used to be human-readable coloured text on the console, with JSON written
only to a file when `CREATE_LOG_FILE=true`. They are now JSON on stdout in all
cases, and `CREATE_LOG_FILE` has been removed — the file it produced was
written inside the container, where nothing read it. Anything parsing the old
console output needs updating.
:::

### Traces, metrics and log export

All three are off by default and nothing leaves your deployment unless you turn
them on. Point the server at any OTLP/HTTP collector to enable them:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://your-collector:4318
OTEL_EXPORTER_OTLP_HEADERS=x-api-key=...   # if your collector needs auth
```

One switch covers all three signals deliberately. Running a metrics pipeline
that nothing is collecting is machinery you cannot see, so with no endpoint set
the SDK is never started: no instrumentation, no exporters, no measurable
overhead. Log export is the one part that is additive rather than all-or-nothing
— stdout is written either way.

**Traces.** Each request produces a trace spanning the HTTP handler, the Nest
controller, and the Postgres, Redis and Prisma calls underneath it — enough to
see which query is making an endpoint slow. Unhandled 5xx exceptions are
recorded on the span with their stack.

**Metrics.** Request rate, error rate and latency come from
`http.server.request.duration`, labelled by route template, method and status
code. Outbound calls to Typesense, SuperTokens and the LLM provider come from
`http.client.request.duration`, labelled by host. Node runtime health covers
event loop delay (mean through p99), event loop utilisation, GC duration by
collector type, and V8 heap usage by space — a stalled event loop is the usual
shape of trouble in a Node process, and request-level data alone will not show
it, because the slow request and the request blocking it are rarely the same
one.

:::note Prisma queries are in traces, not metrics
`db.client.operation.duration` exists, but it comes from the `pg` driver
instrumentation, which only sees the node-postgres client used by the
replication/sync engine. Prisma reaches Postgres through its own Rust engine and
emits **spans but no metrics**, so there is no metric for application query rate
or latency — that lives on the `prisma:engine:db_query` spans inside each
request trace instead.
:::

Metric labels deliberately exclude workspace, user and request ids. Those live
on trace attributes, where one value per request is the point; on a metric each
distinct value is another time series, and per-tenant labels are how a metrics
backend falls over. Pushes happen every 60s by default
(`OTEL_METRIC_EXPORT_INTERVAL`); metrics are cumulative, so a longer interval
costs resolution rather than data.

Any OpenTelemetry backend works: Grafana Tempo/Mimir, Honeycomb, Jaeger,
Sentry, or a local collector fanning out to several.

If you set an endpoint and nothing arrives, set `OTEL_LOG_LEVEL=debug` to
surface the exporter's own diagnostics, which are otherwise silent.

### A local Grafana

You do not have to stand up a backend to look at any of this. An overlay file
ships Grafana, Prometheus, Tempo and an OTel collector in one container, with the
datasources wired together and a Vantik dashboard already provisioned:

```bash
docker compose -f docker-compose.yaml -f docker-compose.observability.yaml up -d
```

Grafana is on [http://localhost:3002](http://localhost:3002) with anonymous admin
access — which is why every port it publishes is bound to `127.0.0.1`. The
overlay sets `OTEL_EXPORTER_OTLP_ENDPOINT` on the server for you and drops
`OTEL_METRIC_EXPORT_INTERVAL` to 5s, because the 60s default means waiting a
minute to see a panel move when you are poking an endpoint by hand.

The **Vantik → Vantik Server** dashboard covers request rate, errors and latency
(overall and per route), outbound call latency per dependency, and Node runtime
health. Traces are in Explore → Tempo; searching `{span.http.route="/some/route"}`
gets you from a slow route to the Prisma and Redis calls underneath it.

Logs land in Loki over the same connection, so a slow trace and the log lines
emitted during it are two clicks apart in either direction. Nothing is scraping
containers to make that work — see [Logs](#logs) above.

What this is not is a production monitoring stack: the image upstream is built
for development and demos, with no auth, no retention policy and all four
components in one container. For a real deployment, point
`OTEL_EXPORTER_OTLP_ENDPOINT` at your own collector instead; nothing in the app
changes.

### Health endpoints

| Endpoint | Meaning |
| --- | --- |
| `GET /` | Liveness. The process is up. Cheap, touches no dependencies. |
| `GET /health/ready` | Readiness. Returns `200` when Postgres, Redis and Typesense all answer, `503` otherwise, with a per-dependency breakdown in the body. |

Point an orchestrator's liveness probe at `/` and its readiness probe at
`/health/ready`. Using readiness for liveness would get the container killed
and restarted over a transient database blip, which fixes nothing.

## FAQ

**Q: Is there a hosted cloud version?**
A: No. Vantik is self-hosted only.

**Q: Can I run Vantik without trigger.dev?**
A: Yes — all core issue tracking works. You lose Actions, user notifications,
and automated cycle transitions.

**Q: Which storage providers are supported for attachments?**
A: Google Cloud Storage and Amazon S3.

If there are any questions that we couldn't answer here, feel free to open an
issue on [GitHub](https://github.com/cmunte132/vantik/issues).
