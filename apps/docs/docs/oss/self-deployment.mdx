## Overview

Vantik is one Docker Compose stack in the main repository. It runs the webapp,
the API server, PostgreSQL, and Redis.
The server applies the database migrations when it starts.
You need no separate repository for the deployment, and no setup script.

This guide gives you a deployment that works. You control the other work: the
scale of the deployment, the backups, and the security beyond the basic level.

## Requirements

- Docker, or Podman with the compose provider. A Podman VM needs 8 GB of memory
  or more to build the images.
- 4 CPUs and 8 GB of RAM is a comfortable minimum.

## Instructions

1. Clone the repository, make your `.env` file, and make the key that
   encrypts the credentials of agent runs. The server does not start without
   the key. Keep it in your backup: with a different key, the server cannot
   read the credentials already saved.

```bash
git clone https://github.com/cmunte132/vantik.git
cd vantik
cp .env.example .env
echo "CREDENTIAL_ENCRYPTION_KEY=$(openssl rand -base64 32)" >> .env
```

2. For a deployment that is more than a test on localhost, edit `.env`:

   - Set `FRONTEND_HOST` and `BACKEND_HOST` to your domain.
   - Change `POSTGRES_PASSWORD`.

3. Start the stack:

```bash
docker compose up -d
```

4. Open the webapp and sign in. The default address is http://localhost:3000.
   Use an email code or a magic link if you configured SMTP.
   Without SMTP, create an account with a passkey.

## How to sign in

There are two methods, and a new installation has both.

**An email code, or a magic link.** Type an address. Vantik then sends you an
email with a code of six digits and a link. This method needs
[SMTP](#email-smtp). In development, the server also writes the code to its log.
If the SMTP server rejects the message, Vantik returns an error instead of a successful login flow.
Check the server log and the SMTP configuration before you try again.

**A passkey.** Authenticate with Touch ID, Windows Hello, or a security key. You
need no mail server, so this is the practical method for one user, or for a
local installation with no SMTP. Sign in with a passkey from the login screen.
You can also add a passkey to an account that exists, under
**Settings → Security**.

A passkey is bound to the hostname that the browser sees, and that name comes
from `FRONTEND_HOST`. If you open the same instance on a different domain, the
browser does not offer the passkeys of the old domain. Therefore set
`FRONTEND_HOST` before people enrol. WebAuthn also needs a secure context: use
HTTPS in production. `localhost` is an exception, and it needs no TLS.

An account can hold more than one passkey. The email code also continues to work.
Add a passkey for each device under **Settings → Security**.
Remove a passkey there if you lose its device.

By default, any person can make an account with a passkey. For an instance that
accepts an invitation only, disable that:

```bash
PASSKEY_SIGNUP_ENABLED=false
```

A person then arrives with an invitation or a login code, and adds a passkey
later from Settings.

### Sessions and upgrades

The server stores a hash of each session token in PostgreSQL.
The browser keeps the token in an httpOnly, SameSite=Lax cookie.
Production cookies require HTTPS. A session has a lifetime of 30 days.
HTTP requests with a session cookie extend the database and cookie expiry when fewer than 15 days remain.
Websocket connections and bearer lookups do not extend the browser session lifetime.
Sign-out revokes the session and closes its websocket connections.
A workspace change updates only the current session. The token stays the same.

The server accepts writes and websocket connections from the origins in `FRONTEND_HOST`.
Use a comma-separated list if the installation has more than one frontend origin.

Before an upgrade from SuperTokens, back up the database.
Stop the old server and the SuperTokens service before you apply the migrations.
The migrations copy passkeys and hash personal access tokens before they remove legacy tables.
The migration stops if a legacy passkey has no account or no matching key.
Keep the original hostname in `FRONTEND_HOST` so existing passkeys can authenticate.
Users must sign in again because the new server does not accept old sessions.


### How to sign in as a different user

An operator can sign in as a different user, to see what that user sees. This
feature is off by default.

> **Warning:** Do not use a short or a shared value for `IMPERSONATION_KEY`. A
> person with this key and an account can sign in as any user.

1. In `.env`, set `IMPERSONATION_KEY` to a long random value.
2. Make the server container again, so that it reads `.env`:

   ```bash
   docker compose up -d server
   ```

3. Sign in to the webapp with your own account.
4. Go to `/x/admin`. No link in the webapp goes to this page.
5. In **UserId**, type the ID of the user. The ID is in the `id` column of
   the `User` table of the database.
6. In **Key**, type the value of `IMPERSONATION_KEY`.
7. Click **Submit**.

![The form on /x/admin, with the UserId and Key fields and the Submit
button](/img/docs/settings/super-admin.png)

The server then replaces your session with a session of that user. If the key
is not set, or if the key is wrong, the server returns 404. To go back to your
own account, sign out, and sign in again.

## Scheduled jobs

Vantik does some of its work on a schedule, and not in response to a request.
The server process runs this work as Bull repeatable jobs, on the Redis that
the stack already needs. No necessary work depends on an optional service. The
server registers each job when it starts, and it writes the schedule to the
log. To see if a job runs, read
`docker compose logs server`.

| Job | Default | Variable | What it does |
| --- | --- | --- | --- |
| Cycle maintenance | hourly | `CYCLE_MAINTENANCE_CRON` | This job applies to a team with the automatic cadence. It completes each cycle after the end date of that cycle. It then moves the unfinished issues, as the preference of the team tells it to, and it makes more future cycles. The job never changes a team that controls its cycles manually. |
| Knowledge decay | `0 3 * * *` | `PAGE_DECAY_CRON` | This job archives each knowledge entry that no person triaged and that the server never served. |

To stop a job, set its variable to `off`.

The knowledge bank has more jobs and more settings. Read
[The Gardener](/fundamentals/knowledge/gardener#settings).

## Optional services

Every service below is optional. If you configure no service, the server writes
an error to the log and continues.

### Email (SMTP)

With SMTP, the server sends login codes, magic links, and notification emails.
In development, the server also writes login codes and links to its log.
A [passkey](#how-to-sign-in) needs no email, so an installation for one user can leave SMTP unset.
Any provider with SMTP authentication works, such as Gmail, Amazon SES, or SendGrid:

```bash
SMTP_HOST=your-smtp-host
SMTP_PORT=587
SMTP_USER=your-smtp-username
SMTP_PASSWORD=your-smtp-password
SMTP_DEFAULT_FROM=noreply@yourdomain.com
```

### AI features

The AI features talk to one endpoint with the OpenAI interface. These are the
features: the AI writes a title, it makes a description longer, it divides an
issue into sub-issues, and it offers a filter. You choose the endpoint. It can
be a hosted service or your own hardware, and you set it in one place:

```bash
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=your-key

# Vantik asks for a tier, and never for the name of a model. The ids are the
# ids that your endpoint serves.
LLM_MODEL=google/gemini-3.8-flash
# Optional. Without it, the decisions use LLM_MODEL too.
# LLM_MODEL_DECISIONS=
```

| Tier | Setting | Serves | If not set |
| --- | --- | --- | --- |
| Default (required) | `LLM_MODEL` | Every built-in text task: issue titles, summaries, descriptions, sub-issues and filters, and generated pages | The AI features are off |
| Decisions (optional) | `LLM_MODEL_DECISIONS` | The decisions the server acts on: knowledge triage, the citation judge, and label and module suggestions | Uses `LLM_MODEL` |

Point the decisions tier at a different model when you want the server's
judgments from a stronger or more careful model than the one that writes text.
Triage asks the decisions model twice and acts only when both answers agree.

People use these four setups:

| Setup | `LLM_BASE_URL` | `LLM_API_KEY` | Notes |
| --- | --- | --- | --- |
| OpenRouter | `https://openrouter.ai/api/v1` | your OpenRouter key | One key, and most models. An id has a namespace, for example `anthropic/claude-sonnet-4.5`. |
| OpenAI | `https://api.openai.com/v1` | your OpenAI key | An id has no namespace, for example `gpt-4o-mini`. |
| LM Studio | `http://localhost:1234/v1` | any value | No data leaves the machine. Use the id from the server tab of LM Studio. |
| Ollama | `http://localhost:11434/v1` | any value | No data leaves the machine, for example `gemma2:2b`. Pull the model before you point a role at it. |

Any other endpoint with the same API works on the same four variables. For
example: vLLM, LiteLLM, or a gateway in your company.

A local server ignores the key, but it still needs the header. For a local
server, therefore, set `LLM_API_KEY` to any text that is not empty.

:::note
If you leave these variables unset, the interface has no AI in it: no button to
write a title, no AI filter, and no AI entry in the slash menu of the editor.
The interface shows no control that cannot work. If you set the variables later,
the features appear on the next page load, and you rebuild nothing. The browser
reads this configuration at runtime from `/api/v1/config`.

The other features do not change. You still create an issue with no title, but
the AI writes no title for you. The issue suggestions still return an assignee
from the search, but they suggest no label.

One request can still reach an AI endpoint: a direct API call. That request fails
with an error, and the error names the variable that you did not set. The server does not answer with a
model that nobody chose.
:::

Two more settings are optional, and only OpenRouter reads them. They record the
use of your installation on the OpenRouter dashboard and on its public
leaderboards:

```bash
LLM_APP_URL=https://vantik.example.com
LLM_APP_NAME=Vantik
```

### Search

PostgreSQL provides full-text search, typo matches through pg_trgm, and vectors through pgvector.
The server combines keyword and vector ranks with reciprocal rank fusion (RRF).
The Compose database image, `pgvector/pgvector:pg18`, includes the required extensions.
If you use your own database, install the pgvector package and make pg_trgm available before you apply the migrations.
The migration user must have permission to create extensions in the application schema.
The migrations create `vector` and `pg_trgm` in the schema from `DATABASE_URL`, which defaults to `vantik`.

:::caution Search upgrade
An ordinary upgrade from the old Compose stack needs no extension relocation.
The new database image supplies the extensions, and the migrations create them.

If your database already has `vector` or `pg_trgm` in another schema, the migration stops with an administrator instruction.
An administrator must move each affected extension to the application schema before the migration can continue:

```sql
ALTER EXTENSION vector SET SCHEMA vantik;
ALTER EXTENSION pg_trgm SET SCHEMA vantik;
```

Run only the command for an extension that already exists in another schema.
Replace `vantik` if the `schema` parameter in `DATABASE_URL` names a different schema.
Then apply the migrations again.
:::

Database triggers update searchable text in each write transaction.
No separate search service or repair job is necessary.
The search reads current issue and knowledge metadata from the source tables.

Leave `EMBEDDINGS_SOURCE` unset for keyword search only.
To add semantic search without a hosted endpoint, set:

```bash
EMBEDDINGS_SOURCE=local
EMBEDDINGS_MODEL=Xenova/all-MiniLM-L6-v2
```

The local model uses the CPU and produces 384-dimensional vectors by default.
The server loads the model only when it needs a vector.
The first load can download model files. For offline use, supply cached model files
or set `EMBEDDINGS_MODEL` to a local model directory.
The local source sends no document text to a hosted endpoint.
The model uses memory in the server process and CPU time for each vector.
Keyword-only search needs neither the model files nor that extra memory.

For an OpenAI-compatible endpoint, set:

```bash
EMBEDDINGS_SOURCE=hosted
EMBEDDINGS_BASE_URL=https://api.openai.com/v1
EMBEDDINGS_MODEL=text-embedding-3-small
EMBEDDINGS_API_KEY=your_API_key
```

These URL and model values are the hosted defaults.
Leave `EMBEDDINGS_API_KEY` unset if your endpoint needs no authentication.
Hosted sources receive document text and search text. Check your endpoint's privacy rules before you enable one.
These settings are separate from the `LLM_*` settings for other AI features.

The worker replaces vectors when the text or configured model changes.
Search uses only vectors from the current source, endpoint, and model with the same dimensions.
The local default uses an HNSW index. Other dimensions use an exact vector scan.
For similar issues, the server can compute an anchor vector before the worker updates its stored vector.
Similar-issue checks use a cosine limit of `0.55`. Near-entry checks use `0.5`.
These limits use the local MiniLM model. Different hosted models can need different limits.
A vector distance is a hint, not a duplicate verdict.
If the source is unavailable, or vectors are not ready, search still returns keyword matches.


### File attachments

The attachments of an issue go to a disk that the server mounts. This is the
default, and it needs no configuration. `docker compose up` gives you a working
upload immediately.

`STORAGE_PROVIDER` selects the backend:

| Value | Where the files go |
| --- | --- |
| `local` | A disk that the server mounts. This is the default. |
| `s3` | Amazon S3, or any store that answers the S3 protocol. |

An empty value means `local`. If you give a name that the server does not have,
the server stops at startup and tells you. If you select a backend but you do
not give it the settings it needs, the server also stops at startup and names
the settings. The server does not start and then fail on the first file.

#### Files on a disk

```bash
# STORAGE_PROVIDER=local is the default. These settings are optional.
LOCAL_STORAGE_PATH=/data/attachments
PUBLIC_ATTACHMENT_URL=https://your-domain.com/api
```

The compose file mounts the volume `attachment-data` at `/data/attachments`.
Keep that volume in your backup. If you remove it, you remove the files.

The server signs the URL of each attachment, and the signature expires. The
server makes the secret that signs them on first start, and keeps it beside the
files. Set `ATTACHMENT_URL_SECRET` yourself in two cases: more than one server
shares the volume, or you want to hold the secret.

#### Object storage

One backend speaks to Amazon S3 and to every store that answers the same
protocol. `S3_ENDPOINT` points it at a store other than Amazon.

```bash
# Amazon S3
STORAGE_PROVIDER=s3
BUCKET_NAME=your-bucket-name
AWS_REGION=your-region
AWS_ACCESS_KEY_ID=your-access-key
AWS_SECRET_ACCESS_KEY=your-secret-key
PUBLIC_ATTACHMENT_URL=https://your-domain.com/api
```

Leave the key and the secret empty on a host that already has credentials, for
example a host with an instance role. The AWS SDK finds them.

For a store that is not Amazon, add `S3_ENDPOINT`:

| Store | `S3_ENDPOINT` | `AWS_REGION` |
| --- | --- | --- |
| Cloudflare R2 | `https://<account-id>.r2.cloudflarestorage.com` | `auto` |
| MinIO | `http://minio:9000` | any value |
| Google Cloud Storage | `https://storage.googleapis.com` | `auto` |
| DigitalOcean Spaces | `https://<region>.digitaloceanspaces.com` | your region |
| Backblaze B2 | `https://s3.<region>.backblazeb2.com` | your region |

`S3_FORCE_PATH_STYLE` puts the name of the bucket in the path and not in the
host name. It becomes true by itself when you set `S3_ENDPOINT`, because most
stores that are not Amazon need it. Set it only if your store needs the other
behaviour.

To try object storage before you pay for it, start the MinIO in the compose
file:

```bash
docker compose --profile s3 up -d minio minio-bucket
```

Then set `STORAGE_PROVIDER=s3`, `S3_ENDPOINT=http://minio:9000`,
`BUCKET_NAME=vantik-attachments`, and the user and password of MinIO as the
access key and the secret.

#### If you used the GCP backend before

The server no longer has a Google Cloud Storage backend of its own. Google Cloud
Storage still works, through the S3 backend and the interoperability endpoint.
Your files stay where they are.

1. Make an HMAC key for the service account that owns the bucket. In the Cloud
   Console, open **Cloud Storage > Settings > Interoperability**.
2. Change your `.env`:

```bash
STORAGE_PROVIDER=s3
S3_ENDPOINT=https://storage.googleapis.com
AWS_REGION=auto
AWS_ACCESS_KEY_ID=your-hmac-key
AWS_SECRET_ACCESS_KEY=your-hmac-secret
BUCKET_NAME=your-bucket-name   # no change
```

3. Remove `GCP_SERVICE_ACCOUNT_FILE`. It has no effect.

A server that still has `STORAGE_PROVIDER=gcp` stops at startup and prints these
steps.

#### CORS

A bucket needs a CORS configuration that accepts the origin of your frontend.
The `local` backend needs no CORS configuration, because the server sends the
files itself.

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "POST", "DELETE", "HEAD"],
    "AllowedOrigins": ["https://your-domain.com"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

### Background jobs

The integrations and the user notifications run inside the server, on the redis
that the stack already needs. There is no separate service to deploy and nothing
to configure: if the server runs, they run.

This was not always true. Until recently both went to trigger.dev, which is
optional and is not in the compose file, so on a default deployment a
notification was never delivered and an integration never fired. That is fixed,
and trigger.dev is no longer part of Vantik.


## Observability

### Logs

The server writes JSON to stdout, one object for each line, at the level in
`LOG_LEVEL`. Collect it with the method that your platform uses for container
logs. You configure nothing.

Each line holds the correlation fields of the request: `reqId`, `wId`, `aId`,
and `opName`. `reqId` comes from the `x-request-id` header. If the caller sends
no such header, the server makes the value, and it returns the value on the
response. `wId` is the workspace, `aId` is the user who acts, and `opName` is
the endpoint. When you enable the traces, each line also holds `traceId` and
`spanId`. From any log line you therefore go to its trace.

Each call to a model writes one line with the context `LLM`. The line holds
`purpose`, the feature that made the call, for example `triage.pair`. It also
holds `role`, `model`, `durationMs`, the token counts, and `finishReason`. A
call that fails writes an error line with the same fields. To find the model
calls, filter on `"ctx":"LLM"`.

> **Warning:** Do not set `LOG_LEVEL=debug` in production if the logs leave
> your control. At this level, each model call also writes its prompt and its
> answer. These can hold issue text and page text.

`OTEL_EXPORTER_OTLP_ENDPOINT` also exports every line over OTLP, with the same
correlation fields as record attributes. This setting **adds** a destination,
and it replaces none. The server writes to stdout in both cases, so your usual
collection of the container logs continues to work, and it needs no
configuration. You run no log shipper, and you mount no container socket.

:::caution Upgrade
The old logs were coloured text on the console for a person to read. The server
wrote JSON to a file only when `CREATE_LOG_FILE=true`. The logs are now always
JSON on stdout, and `CREATE_LOG_FILE` is no longer present. The server wrote
that file inside the container, where nothing read it. You must update any tool
that parses the old console output.
:::

### Traces, metrics, and log export

All three are off by default, and no data leaves your deployment before you
enable them. Point the server at any collector for OTLP over HTTP:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://your-collector:4318
OTEL_EXPORTER_OTLP_HEADERS=x-api-key=...   # if your collector needs authentication
```

One switch controls all three signals, and that is the intent. A metrics
pipeline that nothing collects is machinery that you cannot see. Therefore, with
no endpoint, the server never starts the SDK: no instrumentation, no exporters,
and no measurable cost. The log export is the one part that adds a destination.
The server writes to stdout in both cases.

**Traces.** Each request makes one trace. The trace covers the HTTP handler, the
Nest controller, and the calls below them to Postgres, Redis, and Prisma. You
therefore see the query that makes an endpoint slow. The trace also records an
unhandled 5xx exception on the span, with its stack.

**Metrics.** The rate, the errors, and the latency of the requests come from
`http.server.request.duration`. Its labels are the route template, the method,
and the status code. Calls to hosted models and the LLM provider
use `http.client.request.duration`, with the host as the label.
The metrics for the Node runtime cover the delay of the event loop, from the
mean to p99. They also cover the use of the event loop, the duration of the
garbage collection for each type of collector, and the use of the V8 heap for
each space. An event loop that stops is the usual shape of a problem in a Node
process. The request data alone does not show this problem, because the slow
request and the request that blocks it are rarely the same request.

:::note The Prisma queries are in the traces, and not in the metrics
`db.client.operation.duration` exists, but it comes from the instrumentation of
the `pg` driver. That driver sees only the node-postgres client of the
replication engine. Prisma reaches Postgres through its own Rust engine, and
that engine emits **spans but no metrics**. There is therefore no metric for the
rate or the latency of an application query. That data is on the
`prisma:engine:db_query` spans inside the trace of each request.
:::

The metric labels do not hold the ids of the workspace, the user, or the
request, and that is the intent. Those ids live on the trace attributes, where
one value for each request is the purpose. On a metric, each different value is
another time series, and a label for each tenant is how a metrics backend fails.
The server pushes the metrics every 60 seconds by default, and
`OTEL_METRIC_EXPORT_INTERVAL` controls this period. The metrics are cumulative,
so a longer period costs you resolution, and not data.

Any backend that accepts OTLP works, for example a hosted service, a
self-hosted store, or a local collector that sends the data to several
backends.

If you set an endpoint and no data arrives, set `OTEL_LOG_LEVEL=debug`. The
exporter then shows its own diagnostics, which are silent at the other levels.

### The telemetry contract

This section lists the data that Vantik sends. It is the full interface between
Vantik and your backend. Vantik uses the names of the OpenTelemetry semantic
conventions where a convention exists, so a backend that knows the conventions
shows the data with no setup. A name that starts with `vantik.` has no
convention.

**Services.** Each signal carries these resource attributes:

| Attribute | Server | Browser |
| --- | --- | --- |
| `service.name` | `vantik-server` | `vantik-webapp` |
| `service.version` | The release version | The build id |
| `deployment.environment.name` | `NODE_ENV` | `NODE_ENV` of the build |
| `session.id` | — | A random id for each browser tab |

The browser does not send to your backend directly. It sends OTLP/JSON to
`POST /v1/telemetry/traces` and `POST /v1/telemetry/logs` on the server, and
the server sends the data on to your endpoint, with your headers. Thus the
browser needs no address, no credentials, and no CORS setting. The server sets
`service.name` to `vantik-webapp` on all the data that it relays, so the
relay cannot send data that claims to come from the server. When no endpoint is
set, the webapp does not load its telemetry code, and the relay discards what it
receives.

**Spans.**

| Span | Kind | Where it comes from |
| --- | --- | --- |
| `GET /v1/...` and the other routes | Server | Each API request. The attributes follow the HTTP conventions, and `request.id`, `vantik.workspace_id`, and `vantik.actor_id` identify the request. |
| `prisma:*`, Redis, and Postgres spans | Client | The queries below a request or a job |
| `send <queue>` | Producer | A job added to a Bull queue, with `messaging.system=bull` and `messaging.destination.name` |
| `process <queue>` | Consumer | Each attempt of a job, as a child of the `send` span. `vantik.queue.job` names the job, and `vantik.queue.attempt` counts the attempts. |
| `chat <model>` | Client | Each model call, with the `gen_ai.*` attributes: the provider, the model, the tokens, and the finish reason. `gen_ai.usage.cost` is the cost in USD that the provider billed, when the provider reports it (OpenRouter does). `vantik.llm.purpose` names the feature, and `vantik.llm.role` names the agent role. The span holds no prompt and no answer. |
| `invoke_agent <executor>` | Internal | Each agent run, as the root of its own trace. `vantik.agent_run.id` and `vantik.issue.id` identify the run. When the run ends, the span has its status and the counts of its model calls, retries, and guardrail hits. `vantik.agent_run.extension_went_silent` is set when the Vantik extension stops reporting partway through a run. |
| `agent_phase <phase>` | Internal | Each phase of an agent run: `setup`, `implement`, `verify`, `review`, `revise-N`, and `handback`. A `vantik.model_retry` event marks each model call that the harness retries, a `vantik.guardrail` event marks each time the Vantik extension stops a tool call or asks the agent to continue, and a `vantik.language_server` event marks each language server that the agent's code tools start, or fail to start. |
| `chat <model>` in an agent run | Client | Each model call that the agent makes in its sandbox, as a child of its phase, with `vantik.llm.purpose=agent_run`. `http.response.status_code` is the status of the provider. `gen_ai.usage.input_tokens` includes the tokens read from and written to the prompt cache, which are also in `gen_ai.usage.cache_read.input_tokens` and `gen_ai.usage.cache_creation.input_tokens`. The sandbox host reads each call's usage from the provider's own response as it passes through the egress, and the span carries those figures when the response id matches (`vantik.llm.metered=true`). `gen_ai.usage.cost` is the cost of the call in USD: what the provider billed, when it reports a cost (OpenRouter does), and otherwise the harness's catalog price. `vantik.llm.cost_source` says which (`provider` or `catalog`), and `vantik.llm.catalog_cost` keeps the catalog price next to a billed one, so a difference between the two is visible. Anthropic's web searches are in `vantik.llm.web_search_requests`, and a gateway's routing is in `vantik.llm.upstream_provider` and `vantik.llm.byok`. The `vantik.llm.cost` counter adds up the same costs. The run's spend in Vantik uses the same billed figures. The Vantik extension times the call from the moment the request leaves the sandbox: `vantik.llm.duration`, `vantik.llm.response_time` (until the response headers), and `vantik.llm.time_to_first_token`, all in seconds. |
| `execute_tool <tool>` | Internal | Each tool call of the agent, with `gen_ai.tool.name`. The span holds no command and no output. |
| `replicate <Model> <op>` | Consumer | Each change that the server sends to the browsers |
| `send /` | Producer | Each socket.io message to the browsers, with `messaging.system=socket.io`. Some backends show socket.io as a queue for this reason. |
| `documentLoad`, `documentFetch`, `resourceFetch` | Internal | The load of a page in the browser |
| `GET`, `POST`, and the other methods | Client | Each API call from the browser. The call carries `traceparent`, so the server span of the call is in the same trace. |

**Metrics.** The server sends these metrics. The browser sends no metrics.

| Metric | What it measures |
| --- | --- |
| `http.server.request.duration` | The rate, the errors, and the latency of the requests, for each route |
| `http.client.request.duration` | The calls from the server to other services, for each host |
| `nodejs.eventloop.*`, `v8js.*` | The event loop, the garbage collection, and the V8 heap |
| `process.memory.usage`, `process.cpu.time` | The resident memory and the CPU time of the process |
| `messaging.process.duration` | The time of each attempt of a job, for each queue and job. A failed attempt has `error.type`. |
| `vantik.queue.job.wait` | The time from when a job is ready to when a processor starts it |
| `vantik.queue.jobs` | The jobs in each state (`vantik.queue.state`), for each queue |
| `gen_ai.client.operation.duration` | The time of each model call |
| `gen_ai.client.token.usage` | The input and the output tokens of each model call |
| `vantik.llm.time_to_first_token` | The time from the request of an agent's model call to the first streamed update |
| `vantik.agent_run.finished` | The agent runs that ended, for each executor, status, and failure |
| `vantik.agent_run.duration`, `vantik.agent_run.cost`, `vantik.agent_run.turns` | The time, the cost in USD, and the model turns of each agent run |
| `vantik.agent_run.model_retries` | The model calls that an agent run retried, with the status as `error.type` |
| `vantik.agent_run.language_server.start` | The time, in seconds, for a language server in an agent run to start or to be given up on, by `vantik.language_server` and `vantik.language_server.outcome` (`started`, `failed`, `timeout`) |
| `vantik.agent_run.guardrail` | The times the Vantik extension stopped a tool call or asked an agent to continue, for each rule. A sudden rise can be a sign of prompt injection. |

**Logs.** The server sends each log line, with the `traceId` and the `spanId` of
the span that wrote it. The browser sends two kinds of record:

- An error, at severity `ERROR`, with `exception.type`,
  `exception.message`, and `exception.stacktrace`. `vantik.error.source` tells
  where the browser caught the error: `window`, `unhandledrejection`, or
  `route`.
- A Core Web Vital, as an event named `browser.web_vital`, with
  `web_vital.name` (`LCP`, `INP`, `CLS`, `FCP`, or `TTFB`), `web_vital.value`,
  and `web_vital.rating`.

### A backend in the stack

Vantik includes no observability backend, and it prefers none. To run a
backend next to Vantik, write a `docker-compose.override.yaml` file at the root
of the repository. Docker Compose and podman-compose read this file
automatically. In the file, set `OTEL_EXPORTER_OTLP_ENDPOINT` on the server, and
add the service of your backend:

```yaml
# docker-compose.override.yaml
services:
  server:
    environment:
      OTEL_EXPORTER_OTLP_ENDPOINT: http://collector:4318
      # Optional. The default is 60 seconds, which makes you wait one minute
      # to see a metric change when you test an endpoint by hand.
      OTEL_METRIC_EXPORT_INTERVAL: 5000
  collector:
    image: otel/opentelemetry-collector-contrib
    volumes:
      - ./observability/collector.yaml:/etc/otelcol-contrib/config.yaml:ro
    networks:
      - vantik
```

The repository ignores `docker-compose.override.yaml` and the `observability/`
directory. Thus, your dashboards and the configuration of your backend stay
yours, and you can change to a different backend without a change to a tracked
file. A backend that takes OTLP directly needs no collector: point the endpoint
at the backend.

Bind the ports of a local backend to `127.0.0.1`. Many development images have
no authentication.

A backend that wants a different URL for each signal, for example a URL that
holds an organisation in its path, takes `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`,
`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`, and `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` as
full URLs. These variables come from the OpenTelemetry specification, and the
server and the browser relay both read them.

**Background jobs.** The server does its background work in Bull queues in
Redis: triage, citation checks, page refreshes, agent runs, and cycles. Each
addition of a job is a `send <queue>` span, and each attempt of the job is a
`process <queue>` span below it, so a job is in the trace of the request that
added it. `messaging.process.duration` gives the duration of the attempts, and
`vantik.queue.jobs` and `vantik.queue.job.wait` give the jobs in each state and
the wait time. Any backend that shows traces and
metrics thus shows the jobs, with no queue dashboard.

### Health endpoints

| Endpoint | Meaning |
| --- | --- |
| `GET /` | Liveness. The process is up. This call is cheap, and it touches no dependency. |
| `GET /health/ready` | Readiness. The endpoint returns `200` when PostgreSQL and Redis answer. If either fails, it returns `503` with each dependency's status. |

Point the liveness probe of your orchestrator at `/`, and its readiness probe at
`/health/ready`. Do not use the readiness endpoint for liveness. A short fault
in the database then kills the container and restarts it, and that action
corrects nothing.

## FAQ

**Q: Is there a hosted cloud version?**
A: No. You host Vantik yourself.

**Q: Which storage providers can hold the attachments?**
A: A disk that the server mounts, which is the default and needs no
configuration. Also Amazon S3 and every store that answers the S3 protocol:
Cloudflare R2, MinIO, DigitalOcean Spaces, Backblaze B2, Wasabi, and Google
Cloud Storage through its interoperability endpoint. Read
